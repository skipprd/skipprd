### Features

##### S3 Input: Optional config for depth of prefix to ordered list of objects

By default, Skippr S3 Input plugin tracks S3 Object and S3 List Continuation Tokens in its internal offset database.

For source S3 buckets with a large number of objects, this can result in bloated offset storage resulting in increased IO.

Because Skippr also tracks the latest S3 List Continuation Token in the offset database, much of the IO is mitigated and only objects in the most recent List page are evaluated against the offset database.

However, this leaves a relativity short window for late arriving objects. Late ariving data (Objects) may appear in previous List pages and therefore missed by the plugin which has progressed to the latest List page.

In this scenario, it is useful to track Continuation Tokens for prefix paths to the point where sub-prefixes are guaranteed to have lexicographical order. Therefore, providing a longer window for late arriving objects.

Example:

The depth to the ordered objects in this prefix:
```
data/device_data/tenant_id=acme/source_type=mqtt/year=2024/month=04/day=29/json.gz
1                2            3                 4
                                                ^   Each prefix from here is ordered, so
                                                |   continuation token for S3 List request at depth "4"
```

We thus, in our input plugin we configure the ordered prefix depth, in this case `4`.

```
s3:
  s3_bucket: iot-data
  s3_prefix: data/device_data <-- this could be the root of the bucket, or any other prefix
  s3_prefix_ordered_depth: 4
```

This results in the following list requests being made to S3:

```
enriched/data/tenant_id=acme/
enriched/data/tenant_id=acme/source_type=mqtt/ <- continuation token for these list requests are stored
...
```

This configuration will have most value when these combination of factors are true:

- The source S3 bucket has a large number of objects (typically with the "small object problem")
- Source data can arrive late
- The route prefix (configured in `s3_prefix`) is not ordered, but sub-prefixes are ordered

In many cases, the default configuration of `s3_prefix_ordered_depth: 1` is sufficient and this configuration property can be omitted.
