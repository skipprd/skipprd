# Apache Arrow WAL

Performance, resilience and efficiency are all greatly improved via the new Skippr Write-Ahead-Log (WAL).

The new ingestion WAL is a total re-write of the previous data buffering mechanism. While sharing many characteristics with popular databases systems, the Skippr WAL is optimised for high write volumes and offset tracking. It's somewhat analogous to a Kafka log.

The WAL acts as a durable buffer for data and provides atomic commits of the source data offsets. Ensuring no data is lost and that the ingestion pipeline can resume from the last known good state in the event of failure.

Ingested data is persisted to the WAL on local disk as compressed Apache Arrow Flight. The WAL is periodically compacted to Parquet and promoted to object storage with the data catalog updated with any new partitions and schema changes.

Skipprs new WAL brings several benefits:

### Performance Gains

While Arrow is principally an in memory data format, it's also designed for efficient disk writes with good compression. This significantly reduces the IO overhead of the previous buffering mechanism which is especially beneficial where network storage is used (e.g. AWS EFS).

The previous buffering mechanism was based on a simple file system buffer in json format. This was not only inefficient in terms of IO, but also in terms of CPU and memory usage with the additional serialization and deserialization overhead. Apache Arrow is a zero-copy format, meaning that the data is written to disk in the same format as it is in memory, with no additional serialization or deserialization overhead.

WAL compaction to Parquet is now managed by all ingesting threads, rather than the previous single thread scheduling mechanism. This distribution across all ingesting threads smooths out the compaction process and reduces the time taken to promote Parquet to object storage.


### Resilience

The Skippr implementation of a WAL provides atomic commits of the source data offsets, ensuring no data is lost and that the ingestion pipeline can resume from the last known good state in the event of failure.

Source system offsets (e.g. Kafka Topic + Offset, or, S3 Bucket + Object Key + Object Line) are serialised to a structured binary representation and written as a prefix in the WAL file. A fixed byte integer stores the serialised offset length, followed by the serialised offset bytes and data bytes. This ensures that the offset and ingested data are always written atomically to the WAL. In the event of filesystem errors during write, the recovery process adheres to an all or nothing principle. Recovering each available WAL segment or ignoring a bad segment entirely.

This all or nothing recovery assumes that the source system is idempotent, i.e. that the same data can be re-ingested without causing any side effects. This is a common assumption in data integration systems and is generally true for most data sources (e.g. Kafka, S3, etc).

The WAL is also schema aware, a virtue of Arrows support for schema evolution and data type system. This is especially important in the context of Skippr ingestion, where the source data schemas are not known in advance and can change over time.

While it's Skipprs ingestion responsibility to discover and track schema changes, the WAL ensures that the data is persisted in a format that can be read and written by different versions of the schema.


### Future Features

The WAL is a key component in Skipprs future plans for SQL transformations in stream. With the WAL acting as a durable buffer for Arrow Flight RPC, enabling Skippr to support SQL transformations in stream on the WAL.

##### Apache Datafusion

In addition to Apache Arrow, Skippr now implements the Apache Datafusion project. Datafusion provides a data processing and query execution engine and is enjoying rapid adoption into many popular database systems. Skippr plans to leverage Datafusion to query the WAL and S3 Parquet files with SQL.

Currently, Skippr promotes schemas to datalake catalogs such as Hive and optimized Parquet data for use in datalake query engines such as Athena, Snowlflake, etc. This provides significant value to data engineers and data scientists who can efficiently query the data in the datalake without having to mess around with ELT jobs, defining schemas and handling schema evolution. However, data ingested by Skippr is not available for query until the Parquet is promoted to the datalake.

Skippr plans to leverage Datafusion to make both the object store Parquet data and the local disk WAL data queryable via SQL. This would result in the data being available to query by analysts, time series monitoring, and in stream ML as soon as it's ingested.




# Skippr Credentials File

Inspired by AWS credentials provider, this feature adds support for a Skippr credentials file containing your developer access credentials.

Historically, it's been possible to set a Skippr API Key and Workspace in your Skippr configuration yaml file, e.g:

```
skippr:
  api_token: [SECRET_API_TOKEN]
  workspace: dev
```

or, via Environment variables at runtime:

```
SKIPPR_API_TOKEN=[SECRET_API_TOKEN]
WORKSPACE_NAME=dev
```

Both these existing options remain and are suitable for production configuration.

For convenience to developers reviewing and managing schemas via Skippr CLI on their local machine, it's now possible to define a Skippr credentials file:

```
 cat  ~/.skippr/credentials

[account_lablel-workspace_label]
api_token = [SECRET_API_TOKEN]
workspace = workspace_name
```

It's generally recommended that your `account_label` and `workspace_label` match the machine name for your Skippr account and workspace.
(A workspace is simply a group of pipelines, typically used to separate environments (e.g. dev, test, production, etc), or logical groups (e.g. data_science, datalake, iot_ingress, etc).

e.g.

```
[skippr-dev]
api_token = api_token_for_dev
workspace = dev

[skippr-prod]
api_token = api_token_for_production
workspace = production

```




# SQL Configuration and Metadata Management

Skippr now supports essential pipeline configuration and management tasks via SQL.

For example, when creating a new Skippr ingestion pipeline, a common workflow is to:

- run a sync to initially discover schemas on a sample of data
- pause the pipeline
- review and possibly manually override column schemas
- reset the pipeline (removing data source offsets, the WAL and any buffer files)
- restart the pipeline, syncing all data from the beginning

This whole workflow can now be performed from your local machine via SQL in the Skippr CLI.


Example:

```
SKIPPR_PROFILE=skippr-dev skippr query --sql "DISABLE PIPELINE pipeline_name"
```

In the above example we are setting our SKIPPR_PROFILE environment variable, ensuring we are performing SQL operations against our dev Skippr workspace. The passing the `DISABLE PIPELINE pipeline_name` SQL statement to the Skippr `Query` command.


## PIPELINE

#### Enable Pipeline

```
ENABLE PIPELINE pipeline_name
```

#### Disable Pipeline

```
DISABLE PIPELINE pipeline_name
```

#### Reset Pipeline

Caution, this will reset a pipelines offsets and delete the WAL and local buffers such as dead-letters.
This is useful when you want to re-ingest all data from the beginning AND maintain the schemas previously discovered.

```
RESET PIPELINE pipeline_name
(previously `reset_offsets` config option)
```

#### Drop Pipeline

Caution, this will delete the offsets database, WAL and local buffers such as dead-letters, AND the metadata for the pipeline.
This is useful when you want to completely remove a pipeline and all it's data from Skippr.
NOTE: If you run a sync on the pipeline again, it will re-discover the schemas and start ingesting data from the beginning.
```
DROP PIPELINE pipeline_name
```



## SCHEMA

#### DROP SCHEMA

Drop any known schemas for the pipeline. This is useful when you want to re-sync the pipeline and re-discover the schemas from the beginning.
The pipeline offsets database and WAL are not affected by this operation. So the pipeline will continue to ingest data from the last known good state.

```
DROP SCHEMA pipeline_name
```
(previously `reset_metadata` config option)


## ALTER SCHEMA COLUMN

#### ALTER COLUMN TYPE

Modify the `bike_id` column to an `integer` type
```
ALTER SCHMEA pipeline_name ALTER COLUMN bike_id TYPE INT
```

Complex type example. Here's we altering the field manufacturer (which itself is a nested field of the hardware field) to an `ARRAY` type index by `STRING`:

```
ALTER SCHEMA pipeline_name ALTER COLUMN "hardware.manufacturer" TYPE array<string>
```

#### DROP COLUMN

```
ALTER SCHEMA pipeline_name DROP COLUMN bike_id
```

## Deprecated

The below config options are now deprecated in favour of the new SQL configuration and metadata management.

##### reset_offsets

Both the Environment variable (RESET_OFFSETS) and the pipeline level yaml config option.

##### reset_metadata

Both the Environment variable (RESET_OFFSETS) and the pipeline level yaml config option.
