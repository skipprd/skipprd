# Plugin Architecture Adventures: My Output System Journey in Skippr v4.7.0

One of the most challenging aspects of building a data processing system is designing a flexible architecture that can handle various input and output formats without becoming a maintenance nightmare. In Skippr v4.7.0, I tackled this challenge by completely redesigning our output plugin system. Here's the story of how this evolution unfolded and what I learned along the way.

## The Output Problem

Before v4.7.0, Skippr had a hard-coded output system that primarily focused on AWS Athena. While functional, this approach had significant limitations:

1. **Tight coupling** - Output code was intertwined with core processing logic
2. **Limited extensibility** - Adding a new output destination required extensive changes
3. **No error isolation** - Failures in output processing could affect the entire pipeline
4. **No deadletter support** - Invalid records were simply dropped

As our users' needs evolved, it became clear that we needed a more flexible approach. Users wanted to send data to multiple destinations simultaneously, handle failures gracefully, and add custom output destinations without modifying the core codebase.

## The Trait-Based Plugin System

After examining various design patterns, I settled on a trait-based plugin system that leverages Rust's powerful type system:

```rust
#[async_trait]
pub trait DataOutputPlugin: Send + Sync {
    async fn sync(&self, stream: SendableRecordBatchStream, filename: String) 
        -> Result<(), std::io::Error>;
}
```

This simple trait defines the contract for all output plugins. By implementing this trait, any component can serve as an output destination. The `Send + Sync` trait bounds ensure that our plugins can safely work in a concurrent environment.

## Building a Plugin Factory

With the trait defined, I created a factory system to dynamically instantiate plugins based on configuration:

```rust
pub fn create_output_plugin(plugin_name: &str) -> Box<dyn DataOutputPlugin> {
    match plugin_name {
        "file" => Box::new(file_output::FileOutputPlugin::new()),
        "s3" => Box::new(s3_output::S3OutputPlugin::new()),
        "stdout" => Box::new(stdout_output::StdoutOutputPlugin::new()),
        "athena" => Box::new(athena::DataOutputAwsAthenaPlugin::new()),
        _ => {
            println!("Unknown output plugin: {}, defaulting to file", plugin_name);
            Box::new(file_output::FileOutputPlugin::new())
        }
    }
}
```

This approach allows us to:
1. Select different output plugins at runtime
2. Provide a sensible default when configuration is missing
3. Add new plugins without modifying the core system

## Reorganizing Buffer Directories

Alongside the plugin system, I also reorganized our buffer directories to better support multiple outputs and deadletter handling:

```rust
// Old approach
let output_dir = format!("{}/output", data_dir);

// New approach - separate directories for different buffer types
let output_dir = format!("{}/ingest_buffer", data_dir);
let deadletter_dir = format!("{}/deadletter_buffer", data_dir);
```

This separation provides several benefits:
1. **Clearer organization** - Each buffer has a dedicated directory
2. **Better isolation** - Problems in one buffer don't affect others
3. **Simpler debugging** - It's easier to inspect specific buffer types

## Deadletter Handling: Saving the Rejects

One of the most important features in v4.7.0 was the addition of dedicated deadletter handling:

```rust
// When a record is invalid:
let output_file = format!("{}/{}", deadletter_dir.clone(), &deadletter_file_name.as_str());

buffers.write(&output_file, record.to_string().as_bytes());
buffers.write(&output_file, "\n".as_bytes());
```

Rather than simply dropping invalid records, we now write them to a dedicated deadletter buffer. This preserves data that would otherwise be lost and provides users with the opportunity to fix and reprocess these records later.

## The Buffer Name Challenge

An interesting challenge arose when implementing the buffer system: how to uniquely identify different buffer types while maintaining backward compatibility with existing systems. I settled on a naming convention that encodes the buffer type in the filename:

```rust
pub static deadletter_file_name: Lazy<String> = Lazy::new(|| BufferChunker::encode_chunk_name(
    "deadletters",
    Some(Config::get_pipeline_name().as_str()),
    None,
    None));
```

This approach allows our plugin system to easily identify and route buffers to the appropriate destinations.

## Multiple Output Destinations

With the plugin system in place, supporting multiple output destinations became straightforward:

```rust
async fn output_sync() {
    let output_plugins = [
        "file", "athena", "s3", // Configure based on environment
    ];
    
    for plugin_name in output_plugins {
        if !Config::getenv(&format!("DATA_OUTPUT_{}_ENABLED", plugin_name.to_uppercase()), "")
            .is_empty()
        {
            let plugin = create_output_plugin(plugin_name);
            plugin.sync(stream.clone(), buffer_name.clone()).await?;
        }
    }
}
```

This pattern allows users to configure any combination of output destinations through environment variables, without requiring code changes or recompilation.

## Testing the System

Testing this new plugin architecture presented its own challenges. I increased batch sizes for small file tests to ensure the system could handle larger volumes:

```diff
-    - docker run --name skippre2e -e DATA_SOURCE_BATCH_SIZE_BYTES=2048000 ...
+    - docker run --name skippre2e -e DATA_SOURCE_BATCH_SIZE_BYTES=5048000 ...
```

This change helped identify performance bottlenecks that weren't apparent with smaller data volumes. It's a reminder that realistic testing is essential for data processing systems.

## Lessons Learned

Building this plugin system taught me several valuable lessons about extensible architecture in Rust:

1. **Traits as contracts** - Rust's traits provide a powerful way to define plugin interfaces
2. **Dynamic dispatch** - Using `Box<dyn Trait>` enables runtime plugin selection
3. **Clear separation** - Keeping input, processing, and output logic separate simplifies maintenance
4. **Failure isolation** - Well-designed plugin systems contain failures within plugin boundaries
5. **Configuration over code** - Making behavior configurable via environment variables reduces the need for code changes

The most satisfying outcome was seeing how easily new output plugins could be added. What previously took days of careful code changes now requires just a new struct implementing the `DataOutputPlugin` trait.

## Looking Forward

This plugin architecture sets the foundation for further extensibility in Skippr. In future releases, I plan to:

1. Add support for more output destinations (Kafka, JDBC, etc.)
2. Implement a similar plugin system for transformations
3. Create a formal plugin discovery mechanism for third-party plugins

For fellow Rust developers building extensible systems, I highly recommend exploring trait-based plugin architectures. They provide a clean, type-safe way to build systems that can grow and adapt to changing requirements without sacrificing performance or reliability.

Building a plugin system might seem like a lot of work when compared to just adding another output option, but the long-term benefits in maintainability and extensibility have already proven well worth the investment.
