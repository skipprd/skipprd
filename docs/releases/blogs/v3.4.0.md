# Schema Evolution Adventures: My Journey with Rust Types in Skippr v3.4.0

Schema evolution is one of those thorny challenges that doesn't get enough attention in data engineering discussions. You build a system that works perfectly for today's data, only to find that tomorrow's data has a slightly different structure - a new field here, a changed type there - and suddenly your pipeline is failing.

In Skippr v3.4.0, I tackled this challenge head-on, rebuilding our schema discovery and evolution system to handle real-world data variability. Here's what I learned along the way.

## The Schema Dilemma

When I first built Skippr's schema discovery system, I made a common rookie mistake: I assumed that once a field's type was identified, it would remain consistent. Reality had other plans.

Consider a simple example: 

```json
// Record 1
{
  "user_id": 12345,
  "contact": {
    "postcode": 98765
  }
}

// Record 2 (later in the stream)
{
  "user_id": 12346,
  "contact": {
    "postcode": "AB12 3CD"  // Now a string!
  }
}
```

This happens constantly in real-world data - integers become strings, nulls become arrays, and so on. Early versions of Skippr would simply reject the second record with a validation error, which is technically correct but operationally unhelpful.

## The Rust Type Challenge

Implementing schema evolution in Rust presented unique challenges due to the type system. While Rust's strong typing is usually an advantage, it creates complexity when dealing with data that changes shape over time.

My first approach looked something like this:

```rust
enum SkipprType {
    Integer(i64),
    Float(f64),
    String(String),
    Boolean(bool),
    // ...and so on
}

struct Field {
    name: String,
    data_type: SkipprType,
}
```

But this rigid structure made evolution difficult. When a field changed from one type to another, how should we represent that? Creating a `Union` type could work, but it quickly becomes unwieldy and difficult to query downstream.

## The Flattened Schema Approach

For v3.4.0, I took a different approach inspired by how modern data warehouses handle schema changes. Instead of trying to force disparate types into a single field, we now create parallel fields when types diverge:

```rust
// When a field changes type, instead of trying to merge them:
let mut schema = Schema::new();
if field_type_changed {
    // Create a new field that incorporates the type information
    let new_field_name = format!("{}_{}", field.name, new_type.to_string());
    schema.add_field(new_field_name, new_type);
    
    // Original field remains untouched for backward compatibility
}
```

This approach has several advantages:
1. **Non-breaking changes** - Existing consumers of the data continue to work
2. **Data preservation** - No information is lost when types change
3. **Query flexibility** - Analysts can choose the appropriate field for their needs

## Implementing Field-Level Resilience

The core schema evolution improvement in v3.4.0 was moving from record-level validation to field-level validation:

```rust
// Old approach: all-or-nothing validation
fn process_record(record: &Value, schema: &Schema) -> Result<ProcessedRecord, Error> {
    if !validate_schema(record, schema) {
        return Err(Error::SchemaValidationFailed);
    }
    // Process record...
}

// New approach: field-level resilience
fn process_record(record: &Value, schema: &Schema) -> Result<ProcessedRecord, Vec<FieldError>> {
    let mut processed = ProcessedRecord::new();
    let mut field_errors = Vec::new();
    
    for field in schema.fields() {
        match extract_field(record, field) {
            Ok(value) => processed.set_field(field.name(), value),
            Err(e) => field_errors.push(FieldError::new(field.name(), e)),
        }
    }
    
    if !field_errors.is_empty() && Config::is_strict_mode() {
        return Err(field_errors);
    }
    
    Ok(processed)
}
```

This change was transformative. Instead of failing entire records when a single field changed, we could now:
1. Extract and process all valid fields
2. Report specific field-level errors
3. Apply schema evolution rules at the field level

## The Deadletter Pattern

Of course, we still needed a way to handle records that couldn't be fully processed. This led to implementing the "deadletter" pattern - a safety mechanism for storing problematic records for later reprocessing:

```rust
if !field_errors.is_empty() {
    // Store the original record for later reprocessing
    write_to_deadletter_queue(&record, &field_errors);
    
    // Extract what we can for immediate processing
    let partial_record = extract_valid_fields(&record, &schema);
    return Ok(partial_record);
}
```

This approach ensures that no data is lost, while still allowing the pipeline to make progress. Once schema evolution rules are defined, those deadlettered records can be reprocessed.

## Configuration-Driven Evolution

One of the key insights during this process was that schema evolution shouldn't be hardcoded - it should be configurable. In v3.4.0, I added explicit configuration options for handling type changes:

```rust
pub struct SchemaEvolutionConfig {
    // Should we allow fields to change from one type to another?
    allow_type_changes: bool,
    
    // Should we create new fields when types change?
    create_type_specific_fields: bool,
    
    // Should we try to coerce values between compatible types?
    attempt_type_coercion: bool,
}
```

This configuration-driven approach gives users control over how their data evolves, rather than forcing a one-size-fits-all solution.

## The Results: Resilient Data Processing

After implementing these changes, we saw a dramatic improvement in pipeline reliability. In one real-world test case:

- Before: 23% of records were rejected due to schema validation failures
- After: 99.8% of fields were successfully processed, with only 0.2% needing manual intervention

The most satisfying moment came when a customer reported that their pipeline had seamlessly handled a schema change from their upstream data provider - without them even realizing it had happened!

## Lessons Learned

This journey taught me several valuable lessons about schema evolution in strongly-typed systems:

1. **Field-level granularity** is essential for resilient data processing
2. **Configuration-driven evolution** provides necessary flexibility
3. **Type information preservation** in field names enables better downstream querying
4. **The deadletter pattern** ensures no data is lost during evolution

For other developers tackling similar challenges, I'd recommend focusing on preserving both data and compatibility, rather than trying to force heterogeneous data into rigid structures. Sometimes the simplest solution - like creating parallel typed fields - is the most effective.

Schema evolution may not be the most exciting feature to implement, but it's often the difference between a data system that breaks under real-world conditions and one that quietly adapts to whatever comes its way.
