# Chronological Clarity: My Logging Adventures in Skippr v4.8.7

When building data processing systems, proper logging is your lifeline during debugging sessions. You might think logging is a solved problem - just printf and move on, right? Not quite. In Skippr v4.8.7, I tackled one of the most perplexing logging challenges I've faced: ensuring chronological accuracy across concurrent operations. (This release switched from HashMap to BTreeMap for logs, added timestamps, and re-enabled and fixed the global logger. It also improved error handling in the Athena plugin and time partition parsing.)

## The Problem: Timestamp Chaos

Our previous logging system used a simple HashMap to store log entries:

```rust
pub struct Logger {
    logs: HashMap<Log, usize>,
    buffer_limit: usize,
}
```

While this worked for basic use, it had a fatal flaw: HashMaps don't maintain insertion order. When debugging complex concurrency issues, having logs appear in a seemingly random order made it nearly impossible to understand the sequence of events.

Even worse, our system was actually "deduplicating" logs based on content and tracking counts instead of preserving individual entries:

```rust
let count = self.logs.entry(log).or_insert(0);
*count += 1;
```

This meant that if the same error happened multiple times (but at different moments), we'd lose the temporal information about when each instance occurred.

## The Solution: BTreeMap + Timestamps

The solution required two key changes:

1. Adding timestamps to each log entry:

```rust
#[derive(Debug, Clone, Serialize, Hash, PartialEq, Eq)]
pub struct Log {
    time: chrono::DateTime<chrono::Utc>,
    level: LogLevel,
    message: String,
}
```

2. Using a BTreeMap ordered by timestamp instead of a HashMap:

```rust
pub struct Logger {
    logs: BTreeMap<chrono::DateTime<chrono::Utc>, Log>,
    buffer_limit: usize,
}
```

When logging:

```rust
pub async fn log(&mut self, level: LogLevel, message: String) {
    let log = Log {
        time: chrono::Utc::now(),
        level,
        message
    };

    self.logs.insert(log.clone().time, log.clone());
    // ...
}
```

This ensures that when we iterate through logs (for display or API submission), they're automatically sorted by timestamp:

```rust
"logs": logs.iter().map(|(time, log)| {
    json!({
        "level": log.level.to_string(),
        "message": log.message,
        "time": log.time.to_string(),
    })
}).collect::<Vec<_>>(),
```

## Critical Timing: Panic Handling

One of the trickiest scenarios for logging is during panic situations. Panics can occur in any thread at any time, and ensuring logs are captured before the process exits is essential. (This release improved panic handling and ensured logs are flushed before shutdown.)

I had to carefully structure our panic handling to ensure logs were properly flushed:

```rust
thread::spawn(move || {
    let rt = runtime::Builder::new_multi_thread()
        .enable_all()
        .build()
        .unwrap();

    rt.block_on(async {
        LOGGER
            .write()
            .await
            .log(LogLevel::Error, panic_info_clone)
            .await;
        LOGGER.write().await.flush().await.unwrap();
    });
}).join().unwrap();
```

This spawns a dedicated thread with its own runtime to ensure the panic message gets logged and flushed, even if the main thread is compromised.

## Enhancing Visibility with Better Error Handling

Improved logging is only valuable if you have meaningful information to log. I enhanced our error handling to provide more context in our logs:

```rust
let mut file = BufReader::new(match File::open(&filename) {
    Ok(file) => file,
    Err(err) => {
        println!(
            "Failed to open file {} for reading, Error: {}",
            filename,
            err.to_string()
        );
        continue;
    }
});
```

Instead of letting the program panic on file operations, we now catch errors and log detailed information about what went wrong, making debugging much easier. (This release also improved error handling in the Athena plugin and time partition parsing, and fixed potential unwrap issues in partition value extraction.)

## The Results: Debugging Breakthrough

After implementing these changes, our debugging process became dramatically more effective. In one case, we were able to identify a race condition that only occurred when specific operations happened in a particular sequence - something that would have been nearly impossible to diagnose with our previous logging system.

The chronological ordering of logs allowed us to:

1. Trace the exact sequence of events leading to failures
2. Identify patterns in timing-related issues
3. Understand the flow of data through concurrent processes
4. Detect bottlenecks that were causing unexpected delays

## Lessons Learned

This experience reinforced several important principles that I'll carry forward:

1. **Timestamps are essential** - In concurrent systems, knowing when something happened is often as important as knowing what happened
2. **Order preservation matters** - Using data structures that maintain chronological order is vital for logging
3. **Flush at critical points** - Adding strategic flush operations ensures you don't lose valuable logs during crashes
4. **Context is king** - Rich error messages with file names, operation types, and detailed error information make debugging much easier

While logging might seem like a mundane aspect of software development, getting it right can be the difference between hours of frustrating debugging sessions and quickly identifying the root cause of issues.

For my fellow Rust developers, I highly recommend considering BTreeMap for log storage - it's a simple change that can dramatically improve your debugging experience in concurrent systems.
